# Data for the Robust Rail project

This repository contains all the data used and generated by the Robust Rail
project, and the scripts that drive it through the pipeline: locations (shunting
yards), configurations to generate scenarios, scenarios generated by the
[robust-rail-generator](https://github.com/Robust-Rail-NL/robust-rail-generator),
and plans for those scenarios produced either by the
[robust-rail-solver](https://github.com/Robust-Rail-NL/robust-rail-solver) or the
[robust-rail-planner](https://github.com/Robust-Rail-NL/robust-rail-planner) planner,
which the [robust-rail-evaluator](https://github.com/Robust-Rail-NL/robust-rail-evaluator)
then validates.

Location, scenario and plan each have **one** JSON file, in a single unified
interchange schema shared by all three tools. `robust-rail-generator` exports
the schema this repository's fixtures are validated against (see [Fixture
validation](#fixture-validation) below).

## Repository structure

The repository is organised by location — a shunting yard, either real-world
data or manually constructed. Each location lives in a folder named
`Location_CamelCaseName` (e.g. `Location_KleineBinckhorst`) with this layout:

* `location.json` — the location: track parts, facilities, staff
* `configurations/scenario_config_<name>.json` — hand-written generator inputs.
  Not part of the interchange schema; `check_config.py` (in the generator)
  validates these against the location and material catalogue rather than a
  JSON Schema, since they carry free-form `intent` blocks a schema can't check
* `scenarios/scenario_<name>.json` — scenarios, either generated by
  `robust-rail-generator` or written by hand
* `plans/plan_<name>.json` — plans produced by the solver or the planner for a
  scenario of the same `<name>`. A `plan_<name>.txt` companion, produced by the
  solver container itself, sits alongside it and is gitignored
* `evaluations/eval_<name>.{out,err,txt}` — evaluator output for a plan of the
  same `<name>`, gitignored
* `fixtures/{feasible,infeasible,unresolved}/` — the classified fixture corpus;
  see [Fixture validation](#fixture-validation)
* `config.json` — evaluator business-rule configuration
* `vis_config.json` *(optional)* — configuration for the evaluator's
  visualisation function

A location folder may also carry its own `README.md` and a `location.png` or
`<location_name>.png`.

Currently, the repository holds the following locations:
* [Kleine Binckhorst](./Location_KleineBinckhorst/)
* [Simple Service location](./Location_SimpleService/)

## Running the pipeline

Each stage has its own script, all driven the same way — `--location` to
restrict to one `Location_*` directory, `--version` to pick a Docker image
version (a pipeline configuration, not a shared release number; see each
script's `--help`), and `--dry-run` to print the Docker commands without
running them:

```bash
$ python3 run_generator.py    # configurations/ -> scenarios/
$ python3 run_solver.py       # scenarios/ -> plans/, via the HIP solver
$ python3 run_planner.py      # scenarios/ -> plans/, via the robust-rail-plannerer planner instead
$ python3 run_evaluator.py    # plans/ -> evaluations/
```

or all at once:

```bash
$ python3 run_pipeline.py
```

`run_pipeline.py --use-solver` (the default) runs the full
generator → solver → evaluator chain; `--use-planner` swaps in the planner for
the same three steps. For anything else — a subset, a custom order — use
`--steps` directly (e.g. `--steps generator,solver`), mutually exclusive with
the two shorthand flags. `solver` and `planner` are mutually exclusive with
*each other* within one run regardless of how you asked for them — both write
`plans/plan_<name>.json`, so running both over one location would leave one
tool's output silently overwritten by the other's.

`clear.py` removes generated scenarios, plans and evaluations (`--dry-run` to
preview, `--location` to restrict).

`sweep_seeds.py --location <NAME> --config <config-name> --seeds 1-20` runs one
configuration across a range of seeds and classifies each outcome, always via
the solver (not the planner). The seed only varies the *generator* step — it's
embedded in each per-seed `scenario_config_*.json` and controls the random
scenario that gets generated; the solver step that follows runs with its own
fixed search seed (from `config_solver.yaml`, default 1), unrelated to the
sweep. `--save` writes the classified fixtures into
`fixtures/{feasible,infeasible,unresolved}/`.

## Fixture validation

`fixtures/` is validated in CI (`.github/workflows/validate-fixtures.yml`)
against the JSON Schema `robust-rail-generator` exports from its Pydantic
models, gated on that schema itself being fresh relative to the models it was
exported from. `validate_json.py --schema-dir <path>` runs the same check
locally.

## Location files

Each location file has the following structure.

Each file contains track parts, which can be either
- a `RailRoad`: regular track part with a given length
- a `Switch`: this is a switch which has two tracks connected on one side and one track on the other side
- an `EnglishSwitch`: this is a switch connecting two tracks on both sides of the switch
- an `Intersection`: this is a different kind of switch also connecting two tracks on both sides of the switch
- a `Bumper`: this is the end of a track, each `RailRoad` track must always have exactly one track part on both the A and B sides, and for dead-end tracks this is often a `Bumper`, as well as for incoming tracks.

Each file can contain facilities, which can be maintenance or cleaning parts of the shunting yard. They are defined by an `id`, a `type` (e.g., "Reinigingsperron", "Wasmachine", "Inspectieput"), the `relatedTrackParts` (which track part ids this facility is located), the `taskTypes` or service tasks that can be performed here, the `simultaneousUsageCount` on how many train units can be serviced at the same time, and the `timeWindow` during which servicing can take place.
